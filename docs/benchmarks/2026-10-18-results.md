## Summary

Seven optimizations kept, each measured before and after and committed on its own. All 544 .NET tests (SQLite and
PostgreSQL), golden files, end-to-end tests, the TypeScript check, `dotnet format` and ReSharper inspections stay green.
The JSON wire contract is unchanged.

| 2 | `82ca9f0` | Server: reading a query with a large `in` list | −25% time, −47% allocations |
| 3 | `065e620` | Server: `$batch` with 20 operations | −33% time, −30% allocations |

## Environment

- Apple M1 Pro, macOS (Darwin 25.3), .NET SDK 10.0.203, Node 25.9.0
- BenchmarkDotNet 0.15.8, `DefaultJob`, `[MemoryDiagnoser]`; Vitest `bench`
- Baseline: the full .NET run at `c03856c` (same `src/` and `benchmarks/` as the branch's first commit), plus the
  TypeScript baseline at `79a5155`.

## Method

1. Measure every suite (the baseline).
2. Profile the costliest path: BenchmarkDotNet's EventPipe profiler (`--profiler EP`, speedscope traces) for .NET,
   `node --cpu-prof` on the compiled output for TypeScript.
3. Change one thing.
4. Keep it only for a clear gain (≥ 5% time or fewer allocations) with nothing else slower and every test green.
5. When untouched cases moved too (the machine was noisier at times), re-measure the previous commit in the same
   session. For TypeScript, compare medians of three alternating before/after Vitest runs; single runs vary by ±10%.

Times are means. "Before" is the baseline unless the row says otherwise.

## 1. Binder: `Enumerable` methods resolved once, not by name per call (`4baae95`)

**Why.** Binding the medium query cost 41.6 µs, ten times the small one. In the profile, about 35% of binding was
`Expression.FindMethod`: `Expression.Call(typeof(Enumerable), "Any", …)` searches every `Enumerable` overload on each
call. Another ~10% was `Aggregate` finding `Sum`/`Average`/`Min`/`Max` with a `.Single(...)` scan that calls
`GetParameters()` on every `Enumerable` method.

**Before**

```csharp
private static readonly MethodInfo[] EnumerableMethods = typeof(Enumerable).GetMethods(BindingFlags.Public | BindingFlags.Static);

Expression.Call(typeof(Enumerable), nameof(Enumerable.Any), [elementType], source, Expression.Lambda(body, parameter));

var method = EnumerableMethods.Single(method => method.Name == name && method.IsGenericMethodDefinition
    && method.GetParameters().Length == 2
    && method.GetParameters()[1].ParameterType.GetGenericArguments()[1] == target);
```

**After.** A new `Internal/EnumerableMethods.cs` resolves each generic definition once, statically, using method
groups (checked by the compiler). `Sum` and `Average` become frozen dictionaries keyed by the selector's result type.
Call sites only close the definition.

```csharp
internal static class EnumerableMethods
{
    public static readonly MethodInfo AnyWhere =
        Definition(new Func<IEnumerable<object>, Func<object, bool>, bool>(Enumerable.Any));

    public static readonly MethodInfo OrderBy =
        Definition(new Func<IEnumerable<object>, Func<object, object>, IOrderedEnumerable<object>>(Enumerable.OrderBy));

    /// <summary><c>Sum&lt;TSource&gt;(source, selector)</c> by the selector's result type.</summary>
    public static readonly FrozenDictionary<Type, MethodInfo> Sum = ByResultType(nameof(Enumerable.Sum));

    private static MethodInfo Definition(Delegate method) => method.Method.GetGenericMethodDefinition();
    // …
}

// Call sites
Expression.Call(EnumerableMethods.AnyWhere.MakeGenericMethod(elementType), source, Expression.Lambda(body, parameter));
var method = (node.Op == QueryOperators.Sum ? EnumerableMethods.Sum : EnumerableMethods.Average)[target];
```

| QueryBinding | Before | After | Change | Allocated |
|---|---:|---:|---:|---|
| medium | 41.6 µs | 23.1 µs | −44% | 58.5 KB → 28.0 KB |
| large | 43.0 µs | 28.3 µs | −34% | 62.8 KB → 34.4 KB |
| small | 4.3 µs | 4.4 µs | noise | unchanged (no `Enumerable` calls) |

QueryExecution (medium) allocates 182.2 KB → 148.9 KB; its time is bound by EF Core and SQLite and didn't change.

## 2. Query reader: one clone per `in` list, not per item (`82ca9f0`)

**Why.** The request's `JsonDocument` is disposed once reading finishes, so every literal was `Clone()`d into its own
document to outlive it. A 300-id `in` list therefore built 300 small documents. The profile put almost all of
`QueryJson.Read` (large) in `ReadIn`.

**Before**

```csharp
var items = new List<LiteralNode>();
foreach (var item in list.EnumerateArray())
{
    items.Add(… new LiteralNode(item.Clone(), itemLocation) …);
}
```

**After**

```csharp
// Items are elements of one clone of the list rather than a clone each.
var items = new List<LiteralNode>(list.GetArrayLength());
foreach (var item in list.Clone().EnumerateArray())
{
    items.Add(… new LiteralNode(item, itemLocation) …);
}
```

| QueryReading | Before | After | Change | Allocated |
|---|---:|---:|---:|---|
| large | 31.6 µs | 23.8 µs | −25% | 95.9 KB → 50.4 KB |
| medium | 8.9 µs | 8.7 µs | noise | 14.0 KB → 13.7 KB |
| small | 930 ns | 915 ns | noise | unchanged |

The limits (depth, node count, `in` list length) are still checked before anything is cloned.

## 3. `$batch`: read written rows back per set, not per operation (`065e620`)

**Why.** After `SaveChanges`, every inserted or updated row was read back with its own query and its own binding of
the default projection. That made the response N+1 queries, about 35% of a 20-operation batch in the profile.

**Before**

```csharp
foreach (var operation in batch.Operations)
{
    var applied = _applied[operation.Id];
    var value = operation.Op == BatchOperationKind.Delete ? null : await ReadBackAsync(applied, cancellationToken);
    results.Add(new BatchResult { Id = operation.Id, Value = value });
}
// ReadBackAsync: bind DefaultShape, Filter = KeyPredicate(key), Take = 1, one query per call
```

**After.** One query per set. `SetMapping.KeyPredicate` now takes several keys and builds
`(k1 == v1 && …) || …`, so single and composite keys share one code path. The key columns are added to the projection,
and each operation gets the row with its key.

```csharp
foreach (var set in written.GroupBy(applied => applied.Mapping))
{
    var keys = set.Select(applied => (IReadOnlyList<object?>)[.. mapping.DtoType.Key
        .Select(property => mapping.EntityProperties[property].GetValue(applied.Entity))]).ToList();
    var shape = new QueryBinder(server, policies).DefaultShape(new EntityBound(root, mapping, null, isNullable: false), row, null);
    var keyIndexes = mapping.DtoType.Key.Select(property => row.Add(ExpressionHelpers.Inline(mapping.Bindings[property], root))).ToList();
    var plan = new QueryPlan { PolicyFilter = policies.Filter(mapping), Filter = mapping.KeyPredicate(keys), Take = keys.Count, … };

    var result = await mapping.ExecuteAsync(db, plan, cancellationToken);
    foreach (var (applied, key) in set.Zip(keys))
    {
        // Rows the policy filter hides after the write come back without a value.
        if (result.Rows.FirstOrDefault(candidate => keyIndexes.Select(index => candidate[index]).SequenceEqual(key)) is { } match)
        {
            values[applied.Operation.Id] = Serialize(shape, match);
        }
    }
}
```

**Safety.** The policy filter still applies to the read-back. The filter has at most `MaxBatchOperations` (100) terms,
so EF Core caches at most that many query shapes per set. Added an integration test (SQLite and PostgreSQL):
inserts and updates on one set, including one row updated twice, each come back for their own operation.

| BatchExecution.Execute | Before | After | Change | Allocated |
|---|---:|---:|---:|---|
| 20 operations | 779.4 µs | 521.8 µs | −33% | 536.3 KB → 376.0 KB |
| 1 operation | 117.7 µs | 118.6 µs | noise | unchanged |

"Before" here is the previous commit, re-measured in the same session. A first after-run showed 1 operation at
+16% with three times the usual spread; re-measuring showed it was noise.

## 4. .NET client: one shared, read-only `JsonSerializerOptions` (`90cb60a`)

**Why.** Materializing a single row took 94 µs, and 50 rows took only 182 µs: a large fixed cost per context. The
profile showed System.Text.Json building type metadata from scratch. `RestDataContextOptions` created a new
`JsonSerializerOptions` per instance, and STJ caches metadata per options instance. The options are registered as
**scoped** in DI, so a web app calling a LinqToRest API paid this on every request.

**Before**

```csharp
public JsonSerializerOptions SerializerOptions { get; } = new(JsonSerializerDefaults.Web)
{
    NumberHandling = JsonNumberHandling.Strict,
    Converters = { new JsonStringEnumConverter(allowIntegerValues: false) },
};
```

**After**

```csharp
public JsonSerializerOptions SerializerOptions { get; } = SharedSerializerOptions;

private static readonly JsonSerializerOptions SharedSerializerOptions = CreateSerializerOptions();

private static JsonSerializerOptions CreateSerializerOptions()
{
    var options = new JsonSerializerOptions(JsonSerializerDefaults.Web)
    {
        NumberHandling = JsonNumberHandling.Strict,
        Converters = { new JsonStringEnumConverter(allowIntegerValues: false) },
    };
    options.MakeReadOnly(populateMissingResolver: true);
    return options;
}
```

| ClientMaterialization (new context per query) | Before | After | Change | Allocated |
|---|---:|---:|---:|---|
| 1 row | 94.0 µs | 3.4 µs | **−96%** | 80.5 KB → 7.5 KB |
| 50 rows | 182.0 µs | 82.6 µs | −55% | 197.6 KB → 120.7 KB |
| 200 rows | 458.3 µs | 333.6 µs | −27% | 566.5 KB → 477.0 KB |

New unit test: `Serializer_options_are_shared_by_contexts_and_read_only`.

## 5. .NET client: a captured `in` list encoded as one array (`eca2b64`)

**Why.** `ids.Contains(p.Id)` with 300 captured ids took 67.7 µs and allocated 244 KB. Each item went through
`JsonValues.ToElement`: a new buffer, a writer, a parsed document and a clone, about 800 bytes per value.

**Before**

```csharp
private CallNode In(Expression item, IEnumerable values) =>
    new(QueryOperators.In, [Translate(item), new ListNode([.. values.Cast<object?>().Select(value => Literal(value, item))])]);
```

**After.** The checks per value move into `Sendable` (shared with `Literal`). The list is then encoded once, and its
items are elements of that one array.

```csharp
private CallNode In(Expression item, IEnumerable values)
{
    // The items are elements of one encoded array rather than a document each.
    var list = JsonValues.ToElement(values.Cast<object?>().Select(value => Sendable(value, item)).ToList());
    return new(QueryOperators.In, [Translate(item), new ListNode([.. list.EnumerateArray().Select(element => new LiteralNode(element))])]);
}

/// <summary>The value as it's encoded on the wire (a char as a string); throws for values that can't be sent.</summary>
private static object? Sendable(object? value, Expression expression) => value switch
{
    null => null,
    char character => character.ToString(),
    _ when ScalarTypes.IsScalar(value.GetType()) => value,
    _ => throw NotSupported(expression, $"Values of type {value.GetType().Name} can't be sent."),
};
```

| ClientTranslation | Before | After | Change | Allocated |
|---|---:|---:|---:|---|
| large (300 ids) | 67.7 µs | 33.5 µs | −51% | 243.9 KB → 55.7 KB |
| medium, small | — | — | noise | unchanged (no `in` list) |

The golden files (shared with the TypeScript client) prove the request bodies are byte-for-byte the same.

## 6. .NET client: compiled getters for tracked DTOs (`c95e1ff`)

**Why.** `DetectChanges` was more than half of `SaveChanges`, and about a quarter of it was
`PropertyInfo.GetValue`. Every member of every tracked DTO was read through reflection, as were snapshots, foreign
key sync and identity keys.

**After.** A new `Tracking/Accessors.cs` compiles one getter per member, once per DTO type. It's cached in a
`ConditionalWeakTable`, so a discarded model doesn't leak. Compiling is allowed on the client, which runs the
developer's own code; the "no `Compile()`" rule covers the server's request path only.

```csharp
internal sealed class Accessors
{
    private static readonly ConditionalWeakTable<DtoType, Accessors> Cache = [];

    public Func<object, object?>[] Properties { get; }   // same order as DtoType.Properties
    public Func<object, object?>[] Navigations { get; }
    public Func<object, object?>[] Key { get; }

    public static Accessors For(DtoType type) => Cache.GetValue(type, static type => new Accessors(type));

    private static Func<object, object?> Getter(PropertyInfo property)
    {
        var entity = Expression.Parameter(typeof(object), "entity");
        var value = Expression.Property(Expression.Convert(entity, property.DeclaringType!), property);
        return Expression.Lambda<Func<object, object?>>(Expression.Convert(value, typeof(object)), entity).Compile();
    }
}

// ChangeTracker.DetectChanges — before / after
!Entry.SameValue(property.PropertyInfo.GetValue(entry.Entity), entry.Snapshot[index])
!Entry.SameValue(entry.Accessors.Properties[index](entry.Entity), entry.Snapshot[index])
```

| Before → after (previous commit, same session) | Before | After | Change |
|---|---:|---:|---:|
| ChangeDetection, 50 tracked | 14.4 µs | 12.2 µs | −16% |
| ChangeDetection, 500 tracked | 136.1 µs | 114.3 µs | −16% |
| ClientMaterialization, 200 rows | 333.6 µs | 318.6 µs | −4.5% (477 → 464.5 KB) |

## 7. TypeScript client: snapshots built with a loop (`afa54eb`)

**Why.** In the `node --cpu-prof` profile of materializing 200 rows, JSON parsing took 34% (unavoidable) and
`takeSnapshot` 22.5%. Each snapshot built a `Map` from `members.map(m => [name, value])`, allocating a pair per member
of every DTO.

**Before**

```ts
takeSnapshot(): void {
  this.snapshot = new Map(this.set.members.map((member) => [member.name, copy(this.entity[member.name])]));
  this.navigationSnapshot = new Map(
    this.set.navigations.map((navigation) => [navigation.name, copy(this.entity[navigation.name])]),
  );
}
```

**After**

```ts
takeSnapshot(): void {
  this.snapshot = snapshotOf(this.entity, this.set.members);
  this.navigationSnapshot = snapshotOf(this.entity, this.set.navigations);
}

// A loop rather than new Map(members.map(...)): no [name, value] pair per member and DTO.
function snapshotOf(entity: Dto, members: readonly { readonly name: string }[]): Map<string, unknown> {
  const snapshot = new Map<string, unknown>();
  for (const member of members) {
    snapshot.set(member.name, copy(entity[member.name]));
  }

  return snapshot;
}
```

| materialize (median of 3 alternating runs) | Before | After | Change |
|---|---:|---:|---:|
| 1 row | 16.3 µs | 15.0 µs | −8% |
| 50 rows | 118.8 µs | 108.4 µs | −9% |
| 200 rows | 442.0 µs | 397.2 µs | −10% |

## Rejected or not attempted

| Idea | Outcome |
|---|---|
| Query reader: clone the whole request once (no per-literal clones) | Same gain on large queries, but small and medium allocated 15–28% more. Narrowed to #2. |
| `JsonValues.ToElement` via .NET 10 `JsonElement.Parse` (no pooled document + clone) | Allocations −5%, but time +2–5% in change detection and translation. Reverted. |
| Server response writer: pre-encoded field names (`JsonEncodedText`) | Under 1% of query execution, which SQLite and EF Core dominate. Not attempted. |
| Batch `LoadAsync`: prefetch rows for all updates and deletes per set | About 14% of a 20-operation batch, but it runs ahead of per-operation policy checks and in-order error reporting (security-relevant code). Left as a candidate. |
| Generator (`linqtorest-ts`) | About 40 µs for the whole pipeline in a CLI that runs once per build; process startup dwarfs it. No change justified. |
| TypeScript: compute the identity key once instead of twice | About 2.5%, below what the harness can measure. Left as a candidate. |
| TypeScript: arrays instead of `Map` snapshots | About 16% left in `snapshotOf`; a wider refactor with a modest expected gain. Left as a candidate. |

## Where the time goes now

- **Server query execution.** LinqToRest's own work (reading, compiling, binding) is about 2% of a query on SQLite. The
  gap to hand-written EF Core (medium: about 800 vs 766 µs) comes from the SQL shape, not from LinqToRest's code.
- **Batches.** The remaining cost is EF Core's `SaveChanges`, the transaction, the per-operation `LoadAsync` lookups
  and the read-back queries.
- **Clients.** JSON parsing of the response dominates materialization.

|---|---|---|
